While working at jot.ai in 2021, a colleage came to me with a snippet very alike the one I'm presenting here. He had an enum with one variant containing an option and another with a Vec. Unfortunately for him, it wouldn't compile.

Error E308 is something most of you will have seen: The compiler wasn't able to unify two types during inference. As we know, in Rust each value has exactly one type. But here we try to put two differently-typed iterators into one value. Since he wasn't completely firm in Rust, I gave him an explanation along with three solutions

This is what a competent Rustacean would write back then. No unsafe code, and though the `as_ref` may look a tad complex, it captures what needs to be done. It still incurs one branch in the option match arm.

This solution makes use of dynamic dispatch to unify the iterator types. It incurs no extra branch, but one indirection for each iterator call, in addition to one heap allocation.

Nowadays, we can use dynamic dispatch without using `Box`, so we no longer need the heap allocation, but still incur the dynamic dispatch. This wouldn't have been available back then, because the compiler didn't yet figure out the lifetimes and would have balked at the `&mut _` in the match arms.

This is the option my colleague chose. The `Either` type, supplied by the `either` crate, implements `Iterator` when both `Left` and `Right` types also implement `Iterator` with the same `Item` type. Apart from needing an extra crate, this version incurs a branch on each iteration. On the plus side, the code doesn't allocate, is easy to understand, and here wasn't on the hot path anyway. Besides the either crate already was in our dependencies.

But I felt something was missing. I am also the author of the `optional` crate, which implements a few specialized option-like types that brought some performance benefits mainly before niche optimization was a thing, and for my types I remember I had implemented an `as_slice` method, because it was easy to do, and it gave me an iterator for free. So why didn't `Option` have `as_slice`?

if we had an `as_slice` method, we could simply get a slice from an Option directly, which would make the whole example more readable and less arcane. And get rid of all indirection or allocation.

This is the type as it appears in libcore. As we see if we ignore the slew of annotations, it's an enum with two variants and the `None` variant comes first, which will be useful later. But how does rustc actually put an option in memory?

We get a discriminant, which may be one or four bytes, depending on the architecture (some architectures have problems addressing single bytes). Then we may have some padding and finally a place to put the value if any.

Rust has this thing called niche optimization, where a bit pattern that cannot appear in a valid value will be used to denote `None'. In the case of references, that bit pattern is `null` (usually zeroes). In this case, we can still get the comparison with the None pattern without a branch (on x86 for example that'll be a `sete` instruction) Now let's compare that to how a slice looks in memory

As we can see, the length of the slice is exactly the discriminant of the `Option`. If the length is zero, the type's invariants dictate that the pointer is non-null, so when Rust constructs an empty slice, the pointer will be set to a "dangling" value, that is it doesn't point anywhere useful, but it is not null. The specific position the pointer points to is "don't care" for our intents and purposes, so long as the pointer is correctly aligned and non-null.

The first thing I looked at was whether we already had some method of getting the offset. Unfortunately, the `offset_of!` macro, which was designed for this very purpose was still incomplete back then, notably lacking the capabilities to work with enums at all. So I could either wait or choose a different way to get the offset. If I had `&Some(value)`, I could get the offset by getting a pointer to the `value` and subtracting a pointer to the `Option`. The problem was that our `Option` could be `None`, leaving us without a `value`. So either I would have to ask users to supply `Some(value)` as an extra argument that would then be removed at compile time, or I would have to find another way.

MaybeUninit fit the bill I added the asterisk because the folks who later founded the opsem group decided that they don't want to rule out ABIs where this property isn't guaranteed even if no niche optimization takes place. But for the moment, all looked fine, so I prepared to get this implementation into the standard library.

The way to introduce a library feature into Rust's standard library is to make an ACP and debate for the feature's inclusion. I did so fairly convincingly, and had an implementation ready, so the debate was more on the details.

Implementing an intrinsic sounds very involved and can be very much so. Luckily, this one simply makes a MIR place projection available where the language wouldn't, which made the implementation fairly easy, with a few pointers to know where to look.

From my work on clippy, I know a small bit about MIR, the Rust compiler's Middle Intermediate Representation. It has a thing called "place projection", which encodes things like field accesses. I needed to create a field projection to an enum variant field no matter whether I had that variant. Luckily, all the variant checking is done in the language before it gets compiled to MIR, and constructing the required field projection is quite tractable.

As we can see, the intrinsic definition is just a plain function signature without a body. What we cannot see here is that the signature is just for documentation. The only thing the compiler takes from it is the function name. It would even work if we had omitted the arguments and return type. This is because intrinsics are exempt from signature type checking, because some of them need to do weird things to their type, such as accepting arguments of multiple types – but only some of them.

To be able to typecheck the intrinsic, there's some code that creates a signature to hand to typecheck. This is one arm of a match that is supposed to return a tuple with the number of generic arguments, a vec of input types and the return type. The observant folks in the audience will have noted the `#[lang = ".."] annotation when I showed the Option type, which is what gives us this lang item. In typecheck, we don't really care about the names of generics, we only care about their identity. Which is why our p1 is just another type parameter. As you can see, this is normal Rust code. It arguably looks more intense because I added some explanatory commenbts.

Now that we've typechecked any call to our intrinsic, we need to replace it with the right MIR. This MIR has three parts: First, we get a "projection" that first dereferences our `*const Option` pointer, then unconditionally interprets this as the "Some" variant, and finally gets the zeroeth field (remember we're counting from zero). Second, we take the immutable address of this field. Finally, we assign that to the result. Again, this is normal Rust code, and while I wouldn't expect a new rustacean to come up with it, writing such code is tractable thanks to the compiler docs and the very helpful folks on Rust zulip.

And with that, our `as_slice()` method becomes simpler, directly calling our intrinsic with a pointer to the given `Option`. We won't need to care about offsets, or niche optimizations, because the projection already does the work for us. The length part was changed from an `as` cast to a `usize::from` on request of one reviewer.

I stabilized the method in version 1.75.0 and notified my colleague that his old problem now had a better solution. He was surprised to say the least. Fun story, some people were really unhappy about a new intrinsic in stable, so this apparently sped up the development of the `offset_of!` macro, which just a few weeks later gained the ability to unstably select enum variants. Later the functions were marked `const` because there really wasn't anything holding that back, and the length calculation was simplified to use the discriminant directly instead of calling `is_some()` to speed up compilation. This method would often be inlined, so this would shave a few microseconds off some builds.

Remember the original version I suggested my colleague – which was the thing a competent practicioner would have written. It took one branch and differed in the base pointer, too, which could sometimes preclude other optimizations. So as_slice removes that potential overhead. While I doubt that it'll make a measurable difference in practice, I'd like to think that this small change has made a large number of programs infinitesimally faster.
