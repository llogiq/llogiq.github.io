When looking up methods, the compiler will automatically check all traits implemented on the receiver type to see if they have a method of that name. If there's more or less than one impl, you'll get an error. You can avoid the error on multiple applicable impls by using the turbofish syntax, as shown in the example. You can import traits with `as _` to have them in scope for method lookup, but avoid putting them in the type namespace, which also means they cannot be named in the code.

Sometimes we want to have a generic return type. But now we have two exclusive options: * If we are generic over the return type (as in `AsRef` or `Into`, the trait solver needs to do more work, as there may be multiple implementations on a type. This might lead to the dreaded turbofish to disambiguate the result type. * On the other hand, if we use an associated type, we can have but one implementation per type. The nice thing here is that the trait solver knows the result type from our implementation, and there is no ambiguity. This distinction will become relevant later.

By default, Rust monomorphizes our code. However, we can also choose the trait implementation at runtime with trait objects. Since edition 2018, we have the `dyn` keyword to mark those. They are implemented as fat pointers, containing a base pointer and a pointer to a so-called vtable, which is a data structure the compiler automatically generates for us and which contains the information on where to find the relevant trait functions. The implementation details of this will fill its own talk, so if you're interested, feel free to chat me up later. In general, some restrictions apply. Notably, the compiler won't do type checks at runtime, so we cannot have any associated types with generics. The compiler cannot do associated constants through trait dispatch because of the unclear type at runtime, and the vtable won't contain any functions that have any type parameters (because we wouldn't know how to dispatch on those either) or an opaque return type because again, the compiler may not know the resulting type at compile time. There are also some restrictions regarding the receiver type, which I won't get into. We call functions that follow those restrictions "dispatchable". Now with that all said, let's go into actual standard library traits.

Note that it is considered unidiomatic to implement those traits unless the types really work as arithmetic. Case in point: In the runup to Rust 1.0.0, I suggested implementing `Div` on `Path`s. It was considered too cute and thus denied. On the other hand, the arithmetic traits are often implemented for numbers on one level of references for self, the right-hand-side or both. This is so we don't need to besmirch our formulae by random dereferences.

We also have bit operations that are mostly what you'd expect. There are three things of note here: 1. The circumflex is an xor, not an exponential 2. The bitand and bitor operators unlike the double ampersand and pipe are not short-circuiting 3. The shifts have some custom typechecking logic so that the output type is expected to be the type of the receiver, although the Shl and Shr traits don't require this This can be relevant when replacing the operator with a method call, as the compiler may require a type annotation in some cases. Like the arithmetic traits, the bit ops traits are implemented for numbers on references for self, the right-hand-side or both.

The assign variants take a mutably borrowed self and a right-hand side. Unlike their plain sibling traits, assign variants are usually not implemented for references.

Here we're dealing with equality. If you've been listening to your math teacher, equality relations must be * symmetric (a == b => b == a) * transitive (a == b && b == c => a == c) * consistent (a != b) == !(a == b) Unsafe implementations may not rely on those properties for soundness! Otherwise implementing those traits would be unsafe. There's also the `Eq` trait to mark types whose `PartialEq` implementation is reflexive (for all a, a == a).

We can derive PartialEq and Eq or manually implement them.

This trait implements an order over a type. Implementing it will usually require the following properties: * antireflexivity (!(a < a)) * antisymmetry (a < b => b > a) * transitivity (a < b && b < c => a < c) Again, no unsafe code may rely on those properties, as the traits are safe to implement. The `Ord` trait marks an ordering as a total order. Note also that implementations should be careful to keep the equality and ordering implementation consistent.

We have two traits related to hashing, the Hash and Hasher trait. This lets us decouple the data to hash from the hash algorithm. This lets us write 1 Hash implementation per type we want to hash and 1 Hasher implementation per hash algorithm we want to use. Notably, the standard library's hasher function is relatively slow, but offers good hashdos protection. The Hash trait is usually derived, as is the `PartialEq` trait. There is a relation between these traits, in that if two values are equal according to PartialEq, they should also be hashed to the same hash value. Otherwise HashMap/HashSet lookup will fail to find values or return wrong values. Implementations may not require this relation between `Hash` and `PartialEq` for safety though, because both are safe to implement. Also it is acceptable if two unequal values return the same hash.

This is a valid implementation of Hasher. It fulfils the contract of Hash. Also it is probably the fastest Hasher implementation one can build. Still, it is a very poor implementation, and using it will lead to bad performance, because it hashes all inputs to the same value, thus making HashMaps and HashSets doing a linear scan on lookup and inserts, which turns inserting multiple values into a quadratic operation.

Clone is also known as the "making borrow checker happy" trait. It guarantees not creating mutable shared references. Usually it will do a deep clone of the data, unless inner types share data over their `Clone` implementation. Copy is a marker trait to declare that cloning is a bytewise copy. If you derive Copy, you should also derive Clone, because there is no room for customizing a bytewise copy. Clone is rarely manually implemented, unless there is something special to do (e.g. resources to manage, ref counters to increment, etc.)

The drop trait lets us customize behavior on destruction of a value. This is mostly interesting for types that manage resources, such as * collections, smart pointers and other memory-allocating types, as well as file or network handles * guard types (e.g. std::mem::DropGuard, still nightly only, but also MutexGuard)

Rust's standard library is very keen on conversions. Which is understandable, because those come up a lot in code. Let's go through them one by one.

Those are the traits for direct conversions between types that cannot go wrong. There is no guarantee that the conversion will be cheap. The traits are not defined to be transitive, so if you have type B that implements From<A> and type C that implements From<B>, you don't automatically get From<A> for C. One can use `impl Into<T>` generics in arguments, but it is not commonly done, because it usually hurts compile time. I personally might use it in short, rarely used functions.

Sometimes conversions are only partially defined, or less academically, those conversions can err. The TryFrom and TryInto traits define such conversions. They are blanket defined for infallible conversions. For historical reasons, the error type is defined as `Infallible` and not the never type, even when it is stabilized in the next stable version. The biggest benefit of this trait compared to a plain function is that it can be used in generics.

As with `FromIterator`, the `FromStr` trait doesn't introduce any additional invariants compared to `TryFrom`. However, there is the suggestion of roundtrip-ability with regards to `Display`, but this is not always possible. With that said, the trait is only useful for parsing a string that's already completely in memory, so it e.g. cannot stream.

Clone is only defined on the type itself, not allowing to return a different type. So we have the `ToOwned` trait, which is a superset of `Clone`, adding some extra conversions between e.g. `str` and `String`. This is also basically the inverse to `Borrow` (and also used as such in the Cow type, which by the way is still underused in my not so humble opinion).

`Deref` is basically like `AsRef` … again. But the main difference is that its operation is inserted by the compiler. Therefore it cannot be generic over the target type, but uses an associated type for that. Otherwise the compiler couldn't know which type to choose in most cases. Implementing it for a type is a powerful technique, as it allows method calls on the type a value dereferences to. However, it can also hide what's happening, so for the sake of being able to reason about the code, it is discouraged in the general case. An exception is custom smart pointers and/or guard types which should dereference to what they're pointing to or guarding.

This stuff is what underlies Rust's thread safety, as it encodes in the type system whether a type can be moved or shared across threads. The Sync blanket impl cleverly defines the relationship between the two threads: If you can send a reference, you can share read access.

The default trait is there to allow us to create a usable value of some type. It is implemented for many standard library types, and implementing it will unlock some methods e.g. on the Option type. Also if you have Default implemented on all field types of a struct, you can derive Default for that struct.

Iterators are one of the places where we have lazy computation – many methods only set up the iteration and only a few actually iterate. `IntoIterator` is used in `for` loops and also as a trait bound – having a trait different from `Into` has benefits for trait lookup because we don't need to search through all the other possible `Into` implementations, so we avoid running into ambiguity. The DoubleEndedIterator trait allows us to iterate from both sides. It also allows us to call `.rev()` to reverse the iteration. Interestingly, `rev` is defined on the `Iterator` trait, but only for types that also implement `DoubleEndedIterator`. Iterators have a `fuse` call which means that once iteration is done which is signalled by `next` returning `None`, they will always return `None`. The `FusedIterator` trait can mark iterators to allow the `Fuse` type to specialize for types that need no further checks to uphold this. If you implement `FusedIterator` on a type that is not by itself fused, your code may run into an infinite loop, return wrong results, etc. Fusedness is not a safety guarantee though, so you may not rely on that property in unsafe code. ExactSizeIterator allows us to get the number of items this iterator holds. It requires that the `size_hint` is in accordance with the result of the supplied `len()` method. This requirement is, again, not a safety guarantee. There is the unstable and unsafe `TrustedLen` iterator trait for that.

There's a trick where you can implement `Deref` into a closure type that lets you call your own types. However, this is quite hacky, and I would avoid it.

Async Rust is great because it allows us to have a fairly minimal language surface that lets us build all those state machines to run concurrently. The standard library also contributes a few traits. Notably the future trait is for computations that may finish in the future. Poll by the way is an enum that can be Pending or Ready containing the output. Note that the receiver has a custom type here. I won't go into pinning here though.

All your async fns implicitly return a custom type that implements `IntoFuture`. The only cleverness here is the binding of the IntoFuture type to a Future trait with the right output. This is the main reason we cannot use `Into` here, because we don't know what type will the future be turned into. There is a blanket implemenetation for all futures.

There are basicall three kinds of alternative forms: Different number bases for integers, exponential forms for decimal numbers and floats, and pointers. If they are not implemented, the formatting machinery will use the `Display` implementation as a backup.

For example, you could have a type that is a pair of values, and by implementing the alternative form traits, you could have the output customized for number types.

The `Error` trait has more deprecated methods than non-deprecated ones. It is still good practice to implement it for your error types. The trait is often used with `dyn` trait types. Usually people will use an error library (thiserror, anyhow or recently eros) to implement errors for them.

Rust with very few exceptions keeps track of the sizes of values in our programs: With slices, you usually have them behind a reference, which is internally a fat pointer containing a base pointer + length With dyn trait objects, you get a different kind of fat pointer – you get a pointer to a vtable instead of the length With extern unsized types, we only get a pointer, and we will have to call into external methods to handle everything MetaSized is for both dyn traits and slices – the compiler knows how to obtain the size from the pointer metadata at runtime PointeeSized is for extern unsized types "Unsized" doesn't mean the value is not in memory, it just means we don't know the size at compile time.
